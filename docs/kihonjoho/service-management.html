サービスマネジメントのまとめ

ITILに基づくITサービスマネジメントの各プロセス(インシデント管理・問題管理・変更管理など)や、SLA・BCP・RTO/RPOといった重要な用語・指標、システム監査やITガバナンスを図解しています。読み終えたら下部から問題を解いて定着させましょう。

1サービスマネジメントの全体像(ITIL・SLA・SLM・サービスカタログ)

組織が利用者に提供するITサービスの品質を継続的に維持・向上させるための管理活動を、ITサービスマネジメントという。ITIL(Information Technology Infrastructure Library)は、ITサービスマネジメントにおける成功事例(ベストプラクティス)を体系的にまとめたフレームワークであり、世界的に広く参照されている。

名称分野説明
ITILITサービスマネジメントITサービスマネジメントにおけるベストプラクティスをまとめたフレームワーク
ISMS情報セキュリティ情報セキュリティを組織的・体系的に管理するための仕組み(ISO/IEC 27001に基づき認証取得も可能)
PMBOKプロジェクトマネジメントプロジェクトマネジメントの知識体系をまとめたガイド

ITサービスを提供するにあたっては、提供するサービスの内容や品質の目標をあらかじめ利用者と合意し、その達成状況を継続的に監視・改善していく仕組みが必要である。

用語説明
SLA(サービスレベルアグリーメント)サービス提供者と利用者の間で、稼働率や応答時間などのサービスレベルの目標値を明文化して合意した文書
サービスレベル管理(SLM)SLAで合意したサービスレベルの達成状況を監視し、継続的にサービス品質を維持・改善していくプロセス
サービスカタログ組織が提供可能なITサービスの一覧と、それぞれの内容・利用条件などをまとめた文書
つまずきやすいポイント SLAは提供者と利用者が合意した「文書(目標値)」そのものであるのに対し、SLMはその達成状況を継続的に監視・改善し続ける「プロセス(活動)」である。名称が似ているため混同しやすいが、「文書か、プロセス(活動)か」で区別するとよい。
練習問題 0 / 2問 正解

問1　サービスの提供者と利用者の間で、稼働率や応答時間などのサービスレベルの目標値を明文化して合意したものはどれか。

SLA(サービスレベルアグリーメント)は合意した文書そのもの。SLM(サービスレベル管理)はSLAの達成状況を監視・改善し続けるプロセス。サービスカタログは提供できるサービスの一覧、ITILはITサービスマネジメントのベストプラクティス集。

問2　ITサービスマネジメントのベストプラクティスをまとめたフレームワークはどれか。

ITILはITサービスマネジメントのフレームワーク。ISMSは情報セキュリティを組織的に管理する仕組み、PMBOKはプロジェクトマネジメントの知識体系、CMMIは開発組織のプロセスの成熟度を評価するモデル。

2インシデント管理と問題管理

ITサービスの運用中に発生する障害やトラブルへの対応は、目的の異なる2つのプロセスに分かれる。インシデント管理は「とにかく早くサービスを元に戻すこと」を、問題管理は「二度と同じことが起きないよう根本原因を突き止めること」を目的とする。

項目インシデント管理問題管理
目的サービスを迅速に復旧させる(暫定対応)根本原因を特定し、恒久的な再発防止策を講じる
対応の考え方迅速性を最優先し、応急処置(ワークアラウンド)でよい時間をかけてでも原因究明・恒久対策を優先する
主な成果物ワークアラウンドによるサービス復旧恒久対策の実施、既知の誤り(Known Error)としての登録

問題管理の過程で原因が特定されているが、まだ恒久的な解決に至っていない障害は、「既知の誤り(Known Error)」としてその内容や暫定的な回避策(ワークアラウンド)とともに記録・管理される。同様の障害が再発した際、インシデント管理はこの情報を参照することで迅速に暫定対応できる。

例題: インシデント管理と問題管理の連携 あるサーバでアプリケーションが度々応答しなくなる障害が発生している。インシデント管理では、発生の都度サーバを再起動して速やかにサービスを復旧させる(暫定対応)。並行して問題管理では、なぜ繰り返し応答しなくなるのか根本原因(例: メモリリーク)を調査する。原因は特定できたがすぐに恒久対策(プログラム修正)を適用できない場合、その内容と再起動という回避策を「既知の誤り」として登録しておく。恒久対策を本番環境に適用する際は変更管理のプロセスを経て統制される。
つまずきやすいポイント インシデント管理は「サービスを止めない・早く戻す」ことが目的であり、根本原因の特定は目的としない。一方、問題管理は根本原因の特定・恒久対策の検討が目的であり、必ずしも迅速さを優先しない。この「速さ優先か、原因究明優先か」という目的の違いが問われやすい。
練習問題 0 / 2問 正解

問1　インシデント管理の目的として、適切なものはどれか。

インシデント管理は「サービスを止めない・早く戻す」ことが目的で、根本原因の特定は目的としない。アは問題管理、イは構成管理、エは変更管理の目的。

問2　問題管理の過程で原因は特定されているが、まだ恒久的な解決に至っていない障害として記録されるものはどれか。

既知の誤りとして記録しておくと、同じ障害が起きたときにワークアラウンドを素早く適用できる。変更要求は変更管理に提出する変更の依頼、構成アイテムは構成管理で管理するハードウェアやソフトウェアなどの構成要素。

3変更管理・構成管理・リリース管理

IT環境に変更を加える際には、変更そのものを統制する「変更管理」、変更後の本番環境への展開を担う「リリース管理」、そして構成要素の情報を正確に維持する「構成管理」という、目的の異なる3つのプロセスが連携する。

プロセス目的
変更管理変更が及ぼす影響を評価し、承認・実施・記録を統制することで、変更に伴うリスクを管理する
構成管理IT環境における構成要素(ハードウェア、ソフトウェア等)の情報を正確に把握し、管理する
リリース管理開発・テストが完了したソフトウェアや変更を、本番環境へ計画的に展開・導入する

構成管理では、サーバやソフトウェア、ネットワーク機器などの構成要素(構成アイテム、CI)に関する情報を、構成管理データベース(CMDB: Configuration Management Database)に一元的に記録・管理する。変更管理やリリース管理によって環境に変更が加わった際は、CMDBの情報もあわせて更新され、常に実態と一致した最新の構成情報が維持される。

つまずきやすいポイント 3つのプロセスは連携して動くため混同しやすい。「変更してよいか判断・統制する」のが変更管理、「変更内容を実際に本番環境へ展開する」のがリリース管理、「環境の現状の情報を正確に記録しておく」のが構成管理、という役割分担で覚えるとよい。
練習問題 0 / 2問 正解

問1　IT環境への変更が及ぼす影響を評価し、変更の承認・実施・記録を統制するプロセスはどれか。

変更管理は「変更してよいか判断・統制する」プロセス。リリース管理は承認された変更を本番環境へ計画的に展開し、構成管理は構成要素の情報を正確に記録・維持する。

問2　サーバやソフトウェア、ネットワーク機器などの構成アイテムの情報を記録・維持するデータベースはどれか。

CMDB(構成管理データベース)は構成管理で使う。RFCは変更要求、SLAはサービスレベルの合意、BCPは緊急事態でも重要な事業を継続するための事業継続計画。

4キャパシティ管理・可用性管理・ファシリティマネジメント・財務管理

ITサービスを安定して提供し続けるためには、将来必要となる処理能力を見積もる活動や、サービスが必要なときに利用できる状態を維持する活動、物理的な設備環境を維持する活動、コストを適切に管理する活動など、基盤を支える複数の管理プロセスが必要である。

キャパシティ管理: 将来必要な処理能力を予測し、適切な時期に確保する
可用性管理: サービスが必要なときに利用可能な状態を維持する
ファシリティマネジメント: 電源・空調・入退室管理など物理的な設備環境を維持する
財務管理(ITFM): コストを把握し、予算編成や課金などを適切に行う
プロセス目的
キャパシティ管理将来の業務量やシステム利用状況を予測し、必要な処理能力を適切な時期に確保する
可用性管理合意したサービスレベルに基づき、ITサービスが必要なときに利用可能な状態を維持する
ファシリティマネジメントデータセンタなどの設備において、電源・空調・入退室管理などの物理的な環境を維持・管理する
財務管理(ITFM)ITサービスの提供にかかるコストを把握し、予算編成や課金などを適切に行う
つまずきやすいポイント 「可用性管理」はサービスが止まらず稼働できる状態を維持すること、「キャパシティ管理」は必要な処理能力・容量を確保することが目的であり、どちらも安定稼働に関わるため混同しやすい。可用性管理は主に「止まらないこと(稼働率)」、キャパシティ管理は主に「十分な性能・容量があること」に着目していると整理するとよい。
練習問題 0 / 2問 正解

問1　将来の業務量やシステムの利用状況を予測し、必要な処理能力を適切な時期に確保するプロセスはどれか。

キャパシティ管理は必要な処理能力・容量を確保する。可用性管理は合意したサービスレベルに基づいて、サービスが必要なときに使える状態を維持する。

問2　データセンタなどの設備で、電源・空調・入退室管理などの物理的な環境を維持・管理する活動はどれか。

ファシリティマネジメントは物理的な設備環境を対象とする。財務管理はITサービスの提供にかかるコストを把握し、予算編成や課金などを行う。

5サービスデスクとエスカレーション

利用者からの問い合わせ・障害報告・要望などを一元的に受け付ける窓口をサービスデスクという。サービスデスクは利用者にとっての単一窓口(シングルポイントオブコンタクト)として機能し、自身で解決できない内容は、より高度な知識を持つ上位の担当者や部署へ引き継ぐ。

用語説明
サービスデスク利用者からの問い合わせ・障害報告・要望などを一元的に受け付ける窓口機能
ヘルプデスクサービスデスク機能の中でも、特に技術的な問い合わせや問題解決を専門的に扱う窓口を指すことが多い
エスカレーション担当者だけでは対応できない場合に、より高度な知識・権限を持つ上位の担当者・部署に引き継ぐこと
つまずきやすいポイント サービスデスクは技術的な問い合わせに限らず、利用者からのあらゆる問い合わせ・要望を受け付ける「総合窓口」である。これに対しヘルプデスクは、その中でも技術的な問題解決に特化した窓口を指すことが多い。両者を同一視しがちだが、対象範囲の広さが異なる点を押さえておく。
練習問題 0 / 2問 正解

問1　担当者だけでは対応できない問い合わせを、より高度な知識や権限を持つ上位の担当者・部署に引き継ぐことを何というか。

エスカレーションは、サービスデスクで解決できない場合などに上位の担当へ引き継ぐこと。フェイルオーバーは障害時に待機系へ処理を引き継ぐ仕組み、ワークアラウンドは応急処置、リストアはバックアップからの復元。

問2　サービスデスクの説明として、適切なものはどれか。

サービスデスクは技術的な内容に限らず、あらゆる問い合わせを受け付ける総合窓口。技術的な問い合わせを専門に扱う窓口はヘルプデスクと呼ぶことが多い。ウは問題管理、エは変更管理の役割。

6ITサービス継続性管理と事業継続計画(BCP・RTO・RPO)

事業継続計画(BCP: Business Continuity Plan)は、災害や事故などの緊急事態が発生した際にも、重要な事業を中断させない、あるいは早期に復旧させるための方針・体制・手順を定めた計画である。このうちITサービスに関する部分を担うのがITサービス継続性管理であり、重要なITサービスを継続または早期に復旧できるよう、あらかじめ計画・準備を行う。

指標意味
RTO(目標復旧時間, Recovery Time Objective)障害発生後、業務(サービス)を再開させるまでに許容される最大の時間
RPO(目標復旧時点, Recovery Point Objective)災害や障害の発生時に、どの時点の状態までデータを復旧させる必要があるかを表す指標
例題: RTOとRPOの考え方 あるシステムでRPOが24時間、RTOが4時間と定められているとする。深夜0時に取得した日次バックアップの後、翌日15時に障害が発生した場合、直前のバックアップ(0時時点)まで遡ってデータを復旧すれば、失われるデータは最大15時間分となりRPOの範囲内に収まる。また、障害発生(15時)から4時間以内(19時まで)にサービスを再開できれば、RTOの目標も達成したことになる。RPOは「どこまでデータを遡って復旧するか」、RTOは「復旧までどれだけ時間をかけられるか」という別々の軸の指標である点に注意する。
つまずきやすいポイント RTOとRPOはどちらも「目標」を表す指標だが、RTOは障害発生後の「時間の長さ(いつまでに復旧するか)」、RPOは障害発生時点から見た「データの遡り具合(どの時点まで復旧するか)」を表しており、着目する軸が異なる。「時間(Time)のRTO」「データを戻す地点(Point)のRPO」と対応づけて覚えるとよい。
練習問題 0 / 2問 正解

問1　障害が発生してから、業務(サービス)を再開させるまでに許容される最大の時間を表す指標はどれか。

RTO(目標復旧時間)は「いつまでに復旧するか」という時間の長さ。RPO(目標復旧時点)は「どの時点の状態までデータを戻せればよいか」を表す。MTBFは平均故障間隔、SLAはサービスレベルの合意。

問2　あるシステムのRPOを24時間と定めた。これを満たすために必要な対策として、適切なものはどれか。

RPOが24時間なら、障害発生時点から遡って24時間以内の状態までデータを戻せる必要があるので、24時間以内の間隔でバックアップを取得しておく。イはRTOを24時間とした場合の対策。

7システム運用管理(監視・バックアップ・ログ・パッチ管理)

ITサービスを日々安定して提供するためには、システムの稼働状況を継続的に観測し、データを保護し、操作や作業の記録を残すといった、地道な日常運用管理が欠かせない。

システム監視: 稼働状況を常時観測し、異常の予兆や障害を早期に検知する
バックアップ/リストア: 複製を取得しておき(バックアップ)、障害時に復元する(リストア)
ログ: 操作履歴や障害発生状況を記録し、原因調査などに利用する
パッチ管理: 脆弱性を修正する更新プログラムを適用し、安全な状態を保つ
ジョブスケジューラ: 定めたスケジュールに従いバッチ処理などを自動実行・管理する
用語説明
システム監視システムが正常に稼働しているかどうかを常時観測し、異常の予兆や障害を早期に検知する活動
バックアップシステム障害やデータ消失に備えて、データやシステムの複製をあらかじめ取得しておくこと
リストアバックアップしたデータを用いて、障害発生前の状態にシステムやデータを復元する操作
ログシステムの操作履歴や障害の発生状況などを時系列で記録したデータ。原因調査や不正アクセスの検知に利用する
パッチ管理ソフトウェアの脆弱性を修正する更新プログラム(パッチ)を適用し、システムを最新の安全な状態に保つ管理活動
ジョブスケジューラあらかじめ定めたスケジュールに従って、バッチ処理などのジョブを自動的に実行・管理する仕組み

システムの運用形態には、自社の設備内にサーバやシステムを保有し自ら運用する「オンプレミス」と、インターネット経由でリソースを利用する「クラウドサービス」がある。運用管理の負荷や初期投資、拡張性などの観点で、両者は対比して問われることが多い。

つまずきやすいポイント バックアップは障害に備えて複製を「取得しておく」作業、リストアはその複製を使って「復元する」作業であり、方向(退避か復元か)が逆である点に注意する。また、パッチ管理(ソフトウェアの脆弱性修正)と構成管理(構成情報の記録)は、どちらもIT資産に関わる活動だが目的が異なるため混同しないようにする。
練習問題 0 / 2問 正解

問1　バックアップしたデータを使って、障害が発生する前の状態にシステムやデータを復元する操作はどれか。

リストアは複製を使って「復元する」操作で、バックアップは障害に備えて複製を「取得しておく」作業。ログは操作履歴などの記録、ジョブスケジューラはバッチ処理などを決めたスケジュールで自動実行する仕組み。

問2　ソフトウェアの脆弱性を修正する更新プログラムを適用し、システムを安全な状態に保つ管理活動はどれか。

パッチ管理は更新プログラム(パッチ)の適用を管理する。システム監視は稼働状況を常に観測して異常を早期に検知する活動、ログ管理は操作履歴や障害の発生状況の記録を扱う活動。

8システム監査(目的・監査人の独立性・監査の流れ)

システム監査は、監査対象から独立した立場のシステム監査人が、情報システムのリスクに対するコントロール(管理の仕組み)が適切に整備・運用されているかを点検・評価し、結果を保証したり改善を助言したりする活動である。監査の結果は、監査を依頼した経営者(組織の長)に報告する。

独立性内容
外観上の独立性監査対象の部門と身分上・組織上の関係がないこと(監査対象の業務を担当していない、同じ部門に属していないなど)
精神上の独立性公正かつ客観的な立場で監査判断を行うこと
手順内容
① 監査計画の策定監査の目的・対象・範囲・時期・手続を決める(中長期計画・年度計画・個別計画)
② 予備調査資料の閲覧やアンケートなどで監査対象の実態を把握し、本調査で重点的に見る点を絞る
③ 本調査ヒアリング・現場の観察・記録の突合せなどを行い、結論の裏付けとなる監査証拠を集める。実施した内容と証拠は監査調書にまとめる
④ 評価・結論監査証拠に基づいて、コントロールが適切かどうかを判断する
⑤ 監査報告監査報告書を作成し、依頼者に報告する。必要に応じて改善を勧告する
⑥ フォローアップ勧告した改善が実際に行われているかを確認する(改善を実施するのは監査対象の部門)
つまずきやすいポイント システム監査人は、監査対象の業務に関与してはいけない。改善を「勧告・助言」はするが、改善そのものを実施したり、改善計画を作ったりするのは監査対象の部門である。「監査人が自ら修正する」「監査対象部門の担当者が自部門を監査する」という選択肢は誤り。

問1　システム監査人の独立性について、適切なものはどれか。

システム監査人は監査対象から独立している必要がある(外観上の独立性)。監査人は改善を勧告・助言はするが、改善を実施するのは監査対象の部門なので、イは誤り。アとエは監査対象に関与しているので独立性がない。

問2　システム監査で、ヒアリングや現場の観察、記録の突合せなどを行い、結論の裏付けとなる監査証拠を集める手順はどれか。

本調査で監査証拠を集める。予備調査は資料の閲覧などで実態を把握し、本調査で重点的に見る点を絞る手順。フォローアップは勧告した改善が実際に行われているかを確認する手順。

9ITガバナンスと内部統制の実現

ITガバナンスは、経営陣がITの活用について方針を示し、組織全体でITが適切に使われるよう統制する仕組みである。JIS Q 38500 では、経営陣の役割を「評価(Evaluate)」「指示(Direct)」「モニタ(Monitor)」の3つのタスクとして定めている。

内部統制(「企業と法務」の1つ目の節を参照)を業務の中で実現するためには、次のような仕組みが使われる。

用語説明
職務分掌1人に権限が集中しないよう、仕事の担当と権限を分ける(例: 発注する人と、検収・支払を承認する人を分ける)。不正や誤りを防ぐ
相互牽制複数の人・部署が互いにチェックし合う仕組み
モニタリング内部統制が有効に機能しているかを継続的に評価する活動
ITへの対応業務に組み込まれたITを通じて内部統制を実現すること(アクセス権限の設定、入力チェック、ログの記録など)
レピュテーションリスク企業の評判や信用が下がることによって損失が生じるリスク
つまずきやすいポイント ITガバナンスの主体は情報システム部門ではなく「経営陣」である。職務分掌は「1人で最初から最後まで処理できないように分ける」ことがポイントで、同じ担当者に申請と承認の両方をさせる選択肢は、内部統制上の問題がある例として出題される。
練習問題 0 / 2問 正解

問1　ITガバナンスの主体として、適切なものはどれか。

ITガバナンスは、経営陣がITの活用について方針を示し、組織全体でITが適切に使われるよう統制する仕組み。情報システム部門が主体ではない点に注意する。

問2　1人に権限が集中しないよう、例えば「発注する人」と「検収・支払を承認する人」を分けることを何というか。

職務分掌は、仕事の担当と権限を分けて、1人で最初から最後まで処理できないようにすることで、不正や誤りを防ぐ。モニタリングは内部統制が有効に機能しているかを継続的に評価する活動、レピュテーションリスクは評判の低下で損失が生じるリスク。
