サービスマネジメントのまとめ

ITILの各プロセス(インシデント管理・問題管理・変更管理・キャパシティ管理)を、SLA/OLA/UCの関係や変更諮問委員会(CAB)による統制の仕組みまで踏み込んで整理するとともに、独立した第三者の立場で行うシステム監査についても解説しています。基本情報より一段深い「実務での判断」を意識して読み進めましょう。

1ITILの全体像とSLA・OLA・UCの関係

ITIL(Information Technology Infrastructure Library)は、ITサービスマネジメントにおけるベストプラクティス(成功事例)を体系的にまとめたフレームワークであり、インシデント管理・問題管理・変更管理・キャパシティ管理などのプロセスが定義されている。応用情報では、ITILを他のマネジメント系フレームワークと混同させる出題があるため、それぞれの主眼を区別できるようにしておく必要がある。

名称主眼説明
ITILITサービスマネジメントITサービスの企画・設計・移行・運用・改善に関するベストプラクティスをまとめたフレームワーク
PMBOKプロジェクトマネジメント個別プロジェクトを計画・実行・統制するための知識体系
COBITITガバナンス・統制経営目標達成の観点からITの統制目標を定義し、成熟度を評価するためのフレームワーク
CMMIプロセス成熟度ソフトウェア開発・保守プロセスの成熟度を段階的に評価するモデル

サービス提供者と利用者との間で、提供するサービスの品質・範囲・責任分担などの目標値について合意した文書をSLA(Service Level Agreement, サービスレベル合意書)という。SLAは可用性や応答時間などの目標値を明文化し、サービス品質を測る基準として機能する。応用情報では、SLAを支える2つの関連契約であるOLAとUCの区別まで問われることがある。

用語合意の当事者説明
SLA(サービスレベル合意書)サービス提供者 ⇔ 利用者(顧客)サービス全体として提供者が利用者に約束する品質目標を定めた文書
OLA(運用レベル合意書)提供者内部の部門 ⇔ 部門SLAの目標値を達成するために、提供者組織内の各部門間で取り決める内部合意
UC(引き受け契約)提供者 ⇔ 外部の供給者SLAの目標値を達成するために、外部のサプライヤ(委託先)と取り交わす契約
つまずきやすいポイント SLAは「提供者と利用者(顧客)の間」の合意であるのに対し、OLAは「提供者組織の内部」の合意、UCは「提供者と外部供給者の間」の契約である。SLAで約束した目標値を、組織内部ではOLAで、外部委託先とはUCで裏付けているという入れ子構造を理解しておくと、応用的な出題にも対応しやすい。
練習問題 0 / 2問 正解

問1　SLAで合意したサービスレベルの目標を達成するために、サービス提供者の組織内の部門どうしで取り決める合意はどれか。

OLA(運用レベル合意書)は提供者の内部の合意。SLAは提供者と利用者(顧客)の間の合意、UC(引き受け契約)は提供者と外部の供給者の間の契約。SLMはSLAの達成状況を監視・改善するプロセス。

問2　SLAで合意したサービスレベルの目標を達成するために、サービス提供者が外部の供給者(委託先)と取り交わす契約はどれか。

UC(引き受け契約)は外部の供給者との契約。SLAの目標値を達成するには、提供者の内部(OLA)と外部の委託先(UC)の取り決めが、SLAと矛盾しないようにそろえておく必要がある。CABは変更を審査する変更諮問委員会。

2インシデント管理と問題管理(既知の誤り・KEDB)

サービスの停止など、通常のサービス運用を阻害する未計画の事象をインシデントという。インシデント管理は、根本原因の追求よりもまず迅速なサービス復旧を最優先とするプロセスであり、暫定的な回避策(ワークアラウンド)を用いてでも早期復旧を図る。一方、同種のインシデントが繰り返し発生する場合、その根本原因(問題)を調査・特定し、恒久対策や暫定的な回避策を「既知の誤り(Known Error)」として既知の誤りデータベース(KEDB)に記録・管理するのが問題管理の役割である。

項目インシデント管理問題管理
目的サービスを速やかに復旧させる(暫定対応優先)根本原因を特定し、恒久的な再発防止策を講じる
時間軸の考え方迅速性を最優先し、原因が不明でも復旧を優先する時間をかけてでも原因究明・恒久対策を優先する
主な成果物ワークアラウンドによるサービス復旧既知の誤り(Known Error)としてのKEDBへの登録、恒久対策
つまずきやすいポイント 「繰り返し発生するインシデントの根本原因を調査・特定し、恒久対策や暫定的な回避策を管理するプロセスはどれか」という設問では、選択肢に「インシデント管理」が並ぶことが多いが、根本原因の追求と既知の誤りの管理は問題管理の役割である。インシデント管理はあくまで個々のインシデントへの「その場の対応」であり、恒久対策の検討や既知の誤りの登録までは行わない点を区別する。
練習問題 0 / 2問 正解

問1　繰り返し発生するインシデントの根本原因を調査・特定し、恒久的な対策や暫定的な回避策を管理するプロセスはどれか。

問題管理は時間をかけてでも根本原因を突き止め、再発を防ぐ。インシデント管理は原因が不明でもワークアラウンドで迅速にサービスを復旧させることを優先する。恒久対策の実施にシステムの変更が必要なら、変更管理に変更要求(RFC)を出す。

問2　原因は特定されたが恒久的な解決に至っていない障害を「既知の誤り」として登録し、同じ障害が起きたときに回避策を素早く参照できるようにするデータベースはどれか。

KEDB(既知の誤りデータベース)は問題管理の成果物で、インシデント管理が回避策を探すときに使う。CMDBは構成アイテムの情報を管理するデータベース、サービスカタログは提供できるサービスの一覧。

3変更管理(CAB)とキャパシティ管理

変更管理は、IT環境に対する変更要求(RFC: Request for Change)を受け付け、変更が及ぼす影響を評価したうえで承認・実施・記録を統制することで、変更に伴うリスクを管理するプロセスである。変更の可否は、変更諮問委員会(CAB: Change Advisory Board)による審査を経て決定されることが多く、審査の重さは変更の種類によって使い分けられる。

変更の種類特徴承認プロセス
標準変更あらかじめ承認された定型的な変更(手順が確立し、リスクが低い)個別の審査を省略し、事前承認済みの手順に従って実施
通常変更個別に影響評価が必要な一般的な変更RFCを提出し、CABの審査・承認を経て実施
緊急変更障害対応など、直ちに実施しなければ被害が拡大する変更緊急変更諮問委員会(ECAB)など少人数で迅速に承認
例題: 変更の種類の判断 本番環境で重大な障害が発生し、原因となったモジュールを直ちにロールバックしなければサービス停止が長引く状況を考える。通常の変更と同様にCABの定例審査を待っていては被害が拡大するため、このケースは緊急変更として扱い、少人数の関係者(ECAB相当)による迅速な承認を経て実施するのが適切である。一方、毎月定例で行うパッチ適用のように手順が確立し影響が小さい変更は、都度の個別審査を省略できる標準変更として扱うことができる。変更の種類に応じて承認の重さを使い分ける判断力が、応用情報では問われる。

一方、キャパシティ管理は、現在および将来のサービス需要を予測し、サーバ性能やネットワーク帯域などの処理能力を過不足なく確保・維持することを目的とするプロセスである。ITILでは、対象とする視点の違いから3つの領域に分けて整理されることが多い。

領域着眼点
ビジネスキャパシティ管理将来の事業計画・業務量の変化を踏まえ、中長期的に必要となる容量を予測する
サービスキャパシティ管理提供中の各ITサービスの性能・応答時間を監視し、SLAで合意した水準を維持する
リソースキャパシティ管理サーバ・ストレージ・ネットワークなど個々の資源の使用状況を監視し、逼迫を防ぐ
つまずきやすいポイント 変更管理・構成管理・キャパシティ管理はいずれもIT基盤の統制に関わるため選択肢に並びやすい。「変更してよいか審査・統制する」のが変更管理、「構成要素の情報を正確に記録する」のが構成管理、「将来必要な処理能力を予測・確保する」のがキャパシティ管理と、それぞれの主眼で切り分ける。また可用性管理は「止まらないこと」に着目するのに対し、キャパシティ管理は「性能・容量が足りること」に着目する点も混同しやすい。
練習問題 0 / 2問 正解

問1　本番環境で重大な障害が発生し、原因となったモジュールを直ちに元に戻さなければサービスの停止が長引く。この変更の扱いとして、適切なものはどれか。

直ちに実施しなければ被害が拡大する変更は緊急変更として扱い、少人数で迅速に承認する。通常変更のように定例のCABを待つと停止が長引く。緊急時でも変更管理の統制(承認と記録)は省略しない(エは誤り)。標準変更は手順が確立した低リスクの定型的な変更。

問2　提供中の各ITサービスの性能や応答時間を監視し、SLAで合意した水準を維持するキャパシティ管理の領域はどれか。

サービスキャパシティ管理はサービス単位で性能を見る。ビジネスキャパシティ管理は事業計画を踏まえて中長期的に必要な容量を予測し、リソースキャパシティ管理はサーバやネットワークなど個々の資源の使用状況を監視する。可用性管理はサービスが必要なときに使える状態を維持するプロセス。

4システム監査(独立性と監査プロセス)

システム監査とは、情報システムに関するリスクのコントロール(内部統制)が適切に整備・運用されているかを、監査対象から独立した専門的な立場の監査人が検証・評価する活動である。監査人が監査対象の業務から独立していること(独立性)は、監査意見の客観性・信頼性を担保するうえで不可欠な前提であり、たとえば開発担当者自身が自らの開発したシステムを監査することは認められない。

工程内容
監査計画の策定監査の目的・対象範囲・実施時期などを定める
予備調査監査対象の業務内容や関連資料を事前に把握する
本調査インタビューや資料閲覧、証跡の確認などにより監査証拠を収集する
評価・結論の形成収集した監査証拠に基づき、基準への適合状況を評価する
監査報告発見した問題点や改善勧告を監査報告書としてまとめ、経営層等に報告する
フォローアップ報告した改善勧告への対応状況を、後日改めて確認する

システム監査は、以下のような混同しやすい概念と対比して問われることが多い。内部統制は監査「される側」である経営者・組織が自ら整備・運用する管理の仕組みそのものであり、システム監査はその内部統制が有効に機能しているかを独立した立場で「検証する側」の活動である。またペネトレーションテストは、実際に攻撃を模してシステムの技術的な脆弱性を検証する個別の技術的手法であり、内部統制やコントロール全般の適合性を評価するシステム監査とは対象・観点が異なる。

つまずきやすいポイント 「独立した第三者の立場で検証・評価する」という表現は、システム監査を特徴づけるキーワードである。内部統制は組織が自ら構築・運用する管理の仕組み(監査される対象)であるのに対し、システム監査はその内部統制の整備・運用状況を独立の立場から評価する活動(監査する側)である点を取り違えないようにする。監査を実施する者と監査される業務の担当者が同一であってはならない、という独立性の原則も併せて押さえておく。
練習問題 0 / 2問 正解

問1　システム監査の工程のうち、監査報告書で示した改善勧告への対応状況を、後日改めて確認するものはどれか。

フォローアップでは、監査対象の部門が改善を実施したかを確認する(改善を実施するのは監査人ではなく監査対象の部門)。予備調査は業務内容や資料を事前に把握する工程、本調査はインタビューや証跡の確認で監査証拠を集める工程。

問2　システム監査の説明として、適切なものはどれか。

「独立した立場で検証・評価する」のがシステム監査の特徴。アは内部統制の説明で、監査「される側」が自ら構築・運用するもの。監査人は改善を勧告するが、自ら改善はしない(イは誤り)。
