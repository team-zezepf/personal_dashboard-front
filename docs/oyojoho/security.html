セキュリティのまとめ

公開鍵暗号とハイブリッド暗号方式・デジタル署名の検証手順、SQLインジェクション/XSS/CSRFといったWebアプリケーションへの攻撃とその対策、ゼロデイ攻撃や脆弱性評価指標、多要素認証など、応用情報技術者試験のセキュリティ分野で問われる「仕組みの理解」と「攻防のロジック」を掘り下げて解説します。

1公開鍵暗号方式とハイブリッド暗号方式

公開鍵暗号方式は、暗号化に使う鍵(公開鍵)と復号に使う鍵(秘密鍵)が異なる非対称な暗号方式である。公開鍵は誰でも入手できる形で配布してよく、対応する秘密鍵を持つ本人だけが復号できる。代表例のRSAは「大きな数の素因数分解は計算量的に極めて困難である」という数学的な性質(トラップドア関数)を安全性の根拠としており、公開鍵から秘密鍵を導き出すことは事実上不可能とされている。楕円曲線暗号(ECC)も、より短い鍵長で同等の安全性を実現する非対称暗号として実務で広く使われる。

方式鍵の関係処理速度代表的なアルゴリズム安全性の根拠
共通鍵暗号方式暗号化・復号に同一の鍵を使う高速AES、(旧)DES鍵空間の広さ(総当たり困難性)
公開鍵暗号方式暗号化(公開鍵)と復号(秘密鍵)で異なる鍵を使う共通鍵暗号方式より大幅に低速RSA、楕円曲線暗号(ECC)素因数分解問題・離散対数問題の困難性

公開鍵暗号方式は安全性が高い一方で処理が重く、通信するデータ本体をすべて公開鍵暗号方式で暗号化するのは非効率である。そこで実際の通信(TLS/SSLなど)では、両方式の長所を組み合わせたハイブリッド暗号方式が用いられる。データ本体は高速な共通鍵暗号方式で暗号化し、その共通鍵(セッション鍵)だけを受信者の公開鍵で暗号化して送ることで、速度と鍵配送の安全性を両立させる。

例題: なぜ公開鍵暗号方式だけで済ませないのか 公開鍵暗号方式はRSAなどの数学的処理に基づくため、共通鍵暗号方式(AESなど)に比べて処理コストが桁違いに大きい。大容量のデータ本体を毎回公開鍵暗号方式で暗号化・復号すると通信のたびに大きな遅延が生じる。そこで「重い処理(公開鍵暗号)は小さな鍵の受け渡しだけに使い、重い処理を必要としないデータ本体は軽い処理(共通鍵暗号)に任せる」という役割分担がハイブリッド暗号方式の核心である。
つまずきやすいポイント ハイブリッド暗号方式は「共通鍵暗号方式と公開鍵暗号方式のどちらか」ではなく、両方を組み合わせて使う方式である。「データ本体を暗号化する鍵」と「その鍵を暗号化するための鍵」を混同し、公開鍵でデータ本体を直接暗号化していると誤読しないように注意する。また公開鍵暗号方式では、送信者は受信者の公開鍵で暗号化し、受信者は自分の秘密鍵で復号する(秘密鍵は復号する側だけが保持する)。

2デジタル署名によるなりすまし・改ざんの検知

デジタル署名は、公開鍵暗号方式の鍵の使い方を「秘匿目的とは逆向き」に利用する技術である。通常の公開鍵暗号では「公開鍵で暗号化→秘密鍵で復号」して第三者に読ませないが、デジタル署名では「秘密鍵で暗号化(署名)→公開鍵で復号(検証)」して、本人にしか作れない署名であることを誰でも検証できるようにする。

例題: 署名から確認できる2つのこと 文書が通信途中で改ざんされると、受信者が計算するハッシュ値Aは元の文書と食い違う値になる。一方、署名を復号して得られるハッシュ値Bは送信時点のまま変化しない。したがってA≠Bとなり改ざんを検知できる。また、署名は送信者の秘密鍵でしか作成できないため、公開鍵で正しく復号できたということは対応する秘密鍵の持ち主(=送信者本人)が署名したことの証明にもなる。この2つ目の性質が「送っていないと後から否認できない(否認防止)」という効果を生む。
つまずきやすいポイント ハッシュ関数は鍵を使わない一方向の変換であり、復号できる暗号化とは別物である。また、デジタル署名で使う鍵の向きは通常の公開鍵暗号(秘匿目的)と逆であることに注意する。秘匿目的では「受信者の公開鍵で暗号化→受信者の秘密鍵で復号」だが、デジタル署名では「送信者の秘密鍵で署名→送信者の公開鍵で検証」であり、「誰の」「どちらの」鍵を使うのかを取り違えやすい。

3Webアプリケーションへの攻撃(SQLインジェクション・XSS・CSRF)とWAF

Webアプリケーションは、利用者からの入力を適切に検証・無害化しないと、攻撃者に想定外の操作を許してしまう。代表的な攻撃であるSQLインジェクション・クロスサイトスクリプティング(XSS)・クロスサイトリクエストフォージェリ(CSRF)は、いずれも「入力欄の脆弱性」を突く点は共通するが、不正な処理が「どこで」「誰の権限で」実行されるかが異なる。

攻撃不正な処理が実行される場所仕組みの要点主な対策
SQLインジェクションWebサーバ側のデータベース入力値をエスケープせずSQL文に結合し、攻撃者の文字列がSQL文の一部として実行されるプレースホルダ(バインド機構)の利用、入力値検証
クロスサイトスクリプティング(XSS)閲覧者(被害者)のブラウザ側脆弱なサイトに埋め込まれたスクリプトが、閲覧者のブラウザ上で実行される出力時のエスケープ処理(サニタイジング)
クロスサイトリクエストフォージェリ(CSRF)正規サイト側(被害者の認証状態を悪用)ログイン中の利用者のブラウザに、意図しないリクエストを自動送信させるワンタイムトークンの検証、SameSite属性の設定
例題: SQLインジェクションによる認証突破 ログインフォームのパスワード欄に「' OR '1'='1」のような文字列を入力すると、Webアプリが組み立てるSQL文の条件式が常に真になり、本来のパスワードを知らなくてもログインが成立してしまうことがある。対策の核心は「入力値を文字列としてSQL文に直接連結しない」ことであり、SQL文の雛形に後から値だけを安全に当てはめるプレースホルダ(バインド機構)が有効である。

これらの攻撃はアプリケーションの実装(入力検証やエスケープ処理)を修正するのが根本対策だが、修正が完了するまでの間や、修正が困難な既存システムを保護する手段としてWAF(Web Application Firewall)がある。WAFはWebアプリケーション層の通信内容を検査し、SQLインジェクションのような既知の攻撃パターン(シグネチャ)を検知・遮断する。ネットワーク層の通信可否を判断するファイアウォールとは異なり、HTTPリクエストの中身まで踏み込んで検査する点が特徴である。

つまずきやすいポイント SQLインジェクションは「サーバ側」のデータベースで、XSSは「閲覧者側」のブラウザで、それぞれ不正な処理が実行される。CSRFは情報を盗み出すのではなく、認証済みの利用者になりすまして「意図しない処理を実行させる」攻撃であり、情報窃取が目的のXSSと混同しないよう注意する。またWAFは「通信の中身(攻撃パターン)」を検査する仕組みであり、通信の許可・拒否をルールベースで判断するだけの一般的なファイアウォールとは検査対象の階層が異なる。

4ゼロデイ攻撃と脆弱性の深刻度評価(CVE・CVSS)

ソフトウェアの脆弱性は、発見されてから修正プログラム(パッチ)が提供され、利用者側で適用が完了するまでに一定の時間差がある。この「パッチが存在しない無防備な期間」を狙って行われる攻撃をゼロデイ攻撃と呼ぶ。ベンダーが対策を講じる猶予が「0日」しかない状態で攻撃を受けることが名前の由来である。

無数に発見される脆弱性に優先順位をつけて対応するため、共通の識別・評価の枠組みが整備されている。CVE(Common Vulnerabilities and Exposures)は個々の脆弱性に一意の識別番号を付与し「どの脆弱性か」を特定する仕組みであり、CVSS(Common Vulnerability Scoring System)は攻撃元区分・攻撃条件の複雑さ・必要な権限・影響範囲などの基準に基づき、脆弱性の深刻度を0.0〜10.0の共通尺度で数値化する指標である。CVEが脆弱性の「身分証明書」だとすれば、CVSSはその「危険度スコア」にあたる。

用語役割
CVE個々の脆弱性に一意の番号を付与し、世界共通で識別できるようにする仕組み
CVSS脆弱性の深刻度を、攻撃元区分・攻撃条件の複雑さ・必要権限・影響範囲などから0.0〜10.0のスコアで評価する共通基準
CRYPTREC電子政府推奨暗号リストなど、暗号技術の安全性を評価・監視する日本の政府プロジェクト
ISMS情報セキュリティマネジメントシステム。技術的対策だけでなく組織の運用・管理体制全体をPDCAで管理する枠組み
つまずきやすいポイント ゼロデイ攻撃は「脆弱性の公表・パッチ提供のタイミング」に着目した分類であり、特定の組織を狙う標的型攻撃(手口・対象に着目した分類)や、ハードウェアの物理的な特性を利用するサイドチャネル攻撃、パスワードによく使われる単語を試す辞書攻撃とは分類の軸が異なる。また、CVEは脆弱性を「識別」するための番号、CVSSはその「深刻度を評価」する指標であり、両者の役割を取り違えないようにする。CRYPTRECは暗号方式の安全性評価、ISMSは組織の管理体制という、脆弱性そのものの評価とは異なるレイヤーの仕組みである点も区別しておく。

5多要素認証(MFA)

利用者認証に用いる情報は「知識情報(本人だけが知っている情報)」「所持情報(本人だけが持っている物)」「生体情報(本人の身体的特徴)」の3種類に大別される。このうち異なる種類の要素を2つ以上組み合わせて本人確認を行う方式を多要素認証(MFA)と呼び、いずれか1つの要素が漏えい・盗用されても、他の要素が破られない限りなりすましを防げる点に価値がある。

知識情報: パスワード・暗証番号など。フィッシングやキーロガーによる窃取のリスクがある
所持情報: スマートフォン・ICカードなど。端末紛失やSIMスワップ(乗っ取り)のリスクがある
生体情報: 指紋・顔・虹彩など。漏えい時に「変更」ができない点に注意が必要
例題: SMSワンタイムコードだけでは万全でない理由 SMSで送られるワンタイムコードは「所持情報(スマートフォン)」に基づく認証要素であり、パスワード(知識情報)と組み合わせれば多要素認証になる。ただし、攻撃者が偽サイトでパスワードとその場でSMSコードの両方をリアルタイムに入力させて正規サイトへ中継する手口(リアルタイムフィッシング)や、携帯電話会社を欺いてSIMを乗っ取るSIMスワップ攻撃を使えば、SMSコードも突破されうる。そのため、より強固な認証として、認証アプリが生成するワンタイムパスワードや、フィッシングに強いハードウェアセキュリティキー(FIDO2など)の利用が推奨される場面もある。
つまずきやすいポイント 多要素認証は「異なる種類」の要素を組み合わせる方式であり、同じ種類の情報を2回聞く(例: パスワードと秘密の質問を両方使う)ことは多要素認証にはあたらない。また、シングルサインオン(一度の認証で複数サービスを使える仕組み)は認証の「利便性」を高めるものであり、認証の「強度」を高める多要素認証とは目的の軸が異なるため混同しないようにする。
